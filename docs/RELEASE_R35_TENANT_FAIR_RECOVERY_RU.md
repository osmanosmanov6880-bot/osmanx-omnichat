# OSMANX OMNICHAT R35 — справедливая очередь между компаниями и восстановление целостности

**Дата:** 6 ноября 2026. **Версия:** `3.5.0-recovery`. Основана на реальном восстановленном дереве R34, которое распаковано из проверенного ZIP. **Локальная инженерная сборка, не production.**

## Четыре крупных блока действующего кода

### 1. Двухуровневое SQL-планирование входящих сообщений

`backend/app/inbound_jobs.py`, `backend/app/db.py`, `backend/alembic/versions/f35000a10001_inbound_tenant_fairness.py`

- Первый `row_number()` распределяет очередь внутри каждого внешнего аккаунта по дате события.
- Второй `row_number()` распределяет готовые события между аккаунтами одной компании.
- Финальный выбор предлагает сначала одну попытку каждой компании, а потом следующие. Между проходами учитывается `organizations.inbound_last_dispatched_at`.
- Отметка компании обновляется **в той же транзакции**, что и атомарный захват задания и канала. Если захват проигран, отметка не смещается.
- Сохранён запрет двух одновременных входящих обработчиков для одного канала (R34), а также паузы R32 и ретенция R31.

Это *best-effort fair scheduling*, а не строгое распределение гарантированных квот: одновременно запущенные процессы могут видеть один снимок SQL. Жёсткие гарантии QoS для коммерческих тарифов потребуют отдельного нагрузочного анализа на PostgreSQL.

### 2. Контроль целостности без клиентского содержимого

`backend/app/inbound_maintenance.py`, `GET /api/operations/inbound/integrity`

Диагностика считает:

- просроченные `processing` с завершившимся захватом и без действующей блокировки канала;
- истёкшие блокировки канала без живого задания-владельца;
- ожидающие или неисправимые записи, у которых отсутствует зашифрованное содержимое;
- связи с несуществующим или чужим каналом (только число нарушений).

API не возвращает текст клиента, идентификаторы событий, токены захвата, шифротекст, телефон или идентификатор соцсети. Руководитель (`lead`) может видеть агрегаты, но не исправлять базу.

### 3. Ограниченное восстановление только просроченных захватов

`POST /api/operations/inbound/repair-expired` требует роль owner/admin, CSRF, письменную причину от 12 символов и явный флаг подтверждения.

- Для каждого типа данных за один проход меняется не более 50 записей (`limit_per_category`).
- Просроченное задание с доступным шифротекстом и оставшимися попытками возвращается в `retrying`.
- При исчерпании попыток запись переходит в `failed`, но **зашифрованное событие не стирается**: решение остаётся за человеком.
- Технические записи без содержимого помечаются `expired` без попытки читать несуществующий payload.
- Освобождаются только истёкшие канальные блокировки без активного владельца; SQL CAS не позволяет операции удалить актуальную блокировку или вмешаться в активную работу.
- Нарушенные tenant/channel-связи **не исправляются автоматически**, потому что слепой перенос может раскрыть чужие данные.
- Каждое действие фиксируется как `inbound.repair_expired` в аудите. Операция не отправляет ответы клиентам и не выполняет внешние API-вызовы.

## Безопасное обновление R34 → R35

1. Остановить все старые API/worker-процессы R34.
2. Сделать и проверить копию базы; отдельно сохранить текущие и предыдущие ключи шифрования интеграций. Не помещать секреты в ZIP.
3. Распаковать новый R35 в отдельную папку. **Не смешивать процессы R34 и R35 над одной БД**.
4. С прежним `DATABASE_URL` выполнить `alembic -c backend/alembic.ini upgrade head`, затем `alembic -c backend/alembic.ini check`.
5. Запустить `start_windows.bat` или `start_linux.sh`, проверить «Контроль доставки». Восстановление выполнять только после выяснения причины, и не использовать для проблем с чужими связями.
