# OSMANX OMNICHAT R27 — один отправитель, управляемая очередь

**Релиз:** 5 ноября 2026 года. **Состояние:** проверенная локальная инженерная сборка, не готовый коммерческий SaaS.

## Что изменилось в работающем коде

### 1. Очередь теперь согласовывает отправку между серверами

В R26 уже были независимые захваты заданий. Но два фоновых обработчика могли одновременно отправить **два разных сообщения через один внешний аккаунт**. Это увеличивало риск HTTP 429 и нарушения последовательности ответов одному клиенту. R27 добавляет **одну SQL-блокировку на подключённый аккаунт**, общую для процессов API и workers.

- В `channel_dispatch_leases` только один активный `owner_token` для `channel_id`. Захват выполняется атомарно на SQLite и PostgreSQL, второй конкурент проигрывает без внешнего HTTP-запроса.
- Лизинг захватывается **до** SQL-захвата задания и освобождается только текущим владельцем. Просроченную запись можно безопасно перехватить после сбоя.
- Сервер не выбирает в очередь сообщения занятого отправителя **до лимита результатов**. Поэтому большой накопленный хвост одного аккаунта не вытесняет здоровые компании.
- Фоновый heartbeat обновляет и право на отправителя, и право на само задание **одной SQL-транзакцией**. Если что-либо утрачено, старый обработчик не может восстановить контрольную точку.
- Последний SQL-контрольный переход `mark_send_started` требует актуальную блокировку отправителя и одновременно соблюдает паузы компании/канала из R25–R26.
- Обработчик делает несколько последовательных проходов за цикл, ограниченных числом `limit` (максимум 100 за вызов). Это позволяет отправлять очередь одного аккаунта по порядку, не искусственно растягивая её на один ответ каждые три секунды.
- Контроль доставки показывает только число активных отправителей **своей компании**. Идентификаторы worker, ключи и данные чужих клиентов не раскрываются.

### 2. Удаление компании и безопасность данных

Обновлён `backend/app/extras.py`: при полном удалении рабочей области новые записи `channel_dispatch_leases` удаляются **до** каналов. Это важно для PostgreSQL с реальными ограничениями внешних ключей. Автоматический тест проверяет, что записи другой компании продолжают существовать.

### 3. Миграция R26 → R27

`backend/alembic/versions/f27000a10001_channel_dispatch_lease.py` создаёт таблицу блокировок и индекс `ix_outgoing_account_status`. Существующие диалоги, исходящие задания, контакты, токены и статусы не изменяются. Проверена миграция заполненной SQLite-базы с версии R26 до актуальной ревизии: компания, канал, переписка и сообщение сохранились.

**Обязательно остановить все старые процессы R26 перед обновлением.** Смешанная версия worker (R26 без sender slot и R27 с sender slot) не обеспечивает новую гарантию последовательности.

## Компоненты релиза

- `backend/app/channel_dispatch.py` — SQL-захват, продление, освобождение только владельцем.
- `backend/app/db.py` — `ChannelDispatchLease`, индекс заданий по аккаунту и статусу.
- `backend/app/services.py` — фильтрация занятых аккаунтов до LIMIT, атомарный claim после slot, несколько последовательных проходов, безопасное освобождение.
- `backend/app/outbox_recovery.py` — совместное продление lease+job, последняя контрольная проверка.
- `backend/app/operations.py`, `frontend/src/app.tsx`, `frontend/public/app.js` — компактная индикация активных отправителей.
- `backend/app/extras.py` — безопасный порядок удаления клиента.
- `backend/tests/test_r27_sender_slots.py` — 12 новых SQL/API тестов.
- `scripts/browser_r27_sender_slots.py` — настоящая вкладка «Контроль доставки» в Chromium + локальный FastAPI, 1512 / 390 / 320 px.
- `scripts/verify_r27_postgres.py` — подготовленный сценарий для PostgreSQL 16: **два независимых процесса ОС**, реальная база, блокированный тестовый provider HTTP, проверка отсутствия перекрытия.

## Проверки и ограничения

- **205 серверных теста пройдены** в шести независимых группах; выход каждой группы 0. Единый запуск всего набора иногда зависает при завершении старых тестов; его нельзя выдавать за пройденный. Разделение зафиксировано в CI.
- `tsc --project frontend/tsconfig.json` — прошёл. Это **действующая сборка React 16**, а не React 19.
- Alembic SQLite `upgrade head` и `check` — пройдены, drift отсутствует.
- Chromium: UI по всем трём размерам, без переполнения и JS-ошибок. Во время долгой локальной отправки отображается «Сейчас отправляют: 1 аккаунт», после — 0.
- **PostgreSQL 16 не установлен локально**. Скрипт для CI есть, но выполнение и успешный GitHub Actions workflow в этой среде не подтверждены.
- Запрос `npm view react@19` завершился `EAI_AGAIN`: сборка React 19/Vite не активирована и не объявляется готовой.
- Нет живых подключений WhatsApp/Instagram/Авито/VK/Telegram/MAX/Messenger, публичного HTTPS, независимого security-аудита или нагрузочного испытания. HTTP POST без подтверждения может оставаться неопределённым; R23 изолирует такой случай, но не гарантирует exactly-once доставку.
- Lease TTL 180 секунд и heartbeat 15 секунд — защитная эвристика. При неконтролируемой остановке БД или очень долгом зависшем внешнем запросе необходим контроль времени HTTP, мониторинг и операционная сверка.

## Обновление

1. Остановить все API и worker-процессы R26, **не выполнять rolling update** старых обработчиков с новыми на одной базе.
2. Создать и проверить резервную копию, никогда не класть `.env`, секреты, токены или базы в ZIP.
3. Распаковать R27 отдельно, вернуть конфигурацию только из секретного хранилища.
4. Запустить `alembic -c backend/alembic.ini upgrade head`, затем `alembic -c backend/alembic.ini check`.
5. Запустить `start_windows.bat` или `./start_linux.sh`, открыть `http://127.0.0.1:8000`, проверить «Входящие» и «Контроль доставки» в деморежиме.
6. Перед коммерческим запуском выполнить настоящие PostgreSQL-конкурентные проверки и разрешённые E2E внешних API.
