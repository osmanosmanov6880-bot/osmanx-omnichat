# OSMANX OMNICHAT R29 — атомарные входящие и подтверждение прочтения

Дата: 5 ноября 2026 года. Статус: **локальная инженерная сборка**, не развёрнута на боевом сервере. R29 продолжает восстановленную ветку R19–R28.

## Исправленные проблемы

1. **Конкурирующие входящие.** Раньше два webhook-обработчика могли загрузить одну и ту же версию диалога и записать счётчик непрочитанных по устаревшему состоянию. В R29 `ingest_inbound()` использует атомарный `UPDATE` с SQL-выражениями `unread_count=unread_count+1` и `version=version+1`. Подгруженные значения ORM больше не являются источником нового счётчика.
2. **Запоздавшие события.** `last_inbound_at` и `last_message_at` обновляются монотонно, только если время нового события действительно позднее сохранённого. Старые синхронизированные сообщения не откатывают Inbox назад; история (`history=True`) не увеличивает число непрочитанных.
3. **Прочтение без просмотра.** API `POST /api/conversations/{id}/read` принимает необязательный JSON `{"expected_version": N}`. Если между чтением данных и подтверждением пришло новое сообщение либо произошла смена назначения сотрудника, SQL-проверка версии отклоняет обновление с `409`. Новое сообщение остаётся непрочитанным.
4. **React-интерфейс.** Клиент сперва получает фактически отображаемый диалог, затем подтверждает конкретную версию. При `409` загружает свежие сообщения и показывает один короткий текст по-русски: «Появилось новое сообщение — оно осталось непрочитанным». Повторное уведомление «Новое обращение» не перекрывает объяснение. После успешного подтверждения UI синхронизирует версию, поэтому следующий ответ оператора не вызывает искусственный конфликт.
5. **Ручное «Не прочитано».** SQL-обновление не перезаписывает счётчик свежих входящих устаревшим ORM-значением.

## Гарантии и границы

- Обновление счётчика/версии существует в **той же транзакции**, что и сохранённое входящее сообщение. Если SQL-транзакция откатится, оба изменения откатятся.
- Уже существующая дедупликация по `(conversation_id, external_id)` и проверка подписанных webhook-событий сохранены. *Точно-один-раз на всех возможных внешних API* не заявляется: у провайдеров могут быть повторы или недоступность.
- Дополнительная проверка `organization_id`, `channel_id` защищает от обновления чужого диалога; подтверждение прочтения повторно проверяет назначение оператора прямо в SQL.
- Старые клиенты без JSON-тела продолжают работать: сервер применяет CAS по версии, прочитанной непосредственно перед изменением. **Для полного UX-защитного эффекта обновить и фронтенд**, который передаёт `expected_version`.
- Новая миграция **не нужна**: R29 использует существующие колонки и индексы схемы R28. Нужно обновить API и фронтенд **вместе**.

## Проверки

- Python: `PYTHONPATH=backend:. pytest -q backend/tests/test_r29_inbound_cas.py` — 9 новых сценариев.
- Chromium: `PYTHONPATH=backend:. python scripts/browser_r29_unread_race.py` — автоматически создаёт конфликт между показом переписки и подтверждением прочтения на 1512, 390 и 320 px.
- Компиляция: `tsc --project frontend/tsconfig.json`.
- Схема: `DATABASE_URL=sqlite:///./r29-schema.db PYTHONPATH=backend:. alembic -c backend/alembic.ini upgrade head` и `alembic check`.
- PostgreSQL: `scripts/verify_r29_postgres.py` подключён в `.github/workflows/ci.yml`. Здесь **не запускался**, поскольку PostgreSQL/psycopg в текущем окружении отсутствуют. Он запускает 4 конкурентные сессии на настоящем сервере, проверяет счётчики и CAS.

## Обновление с R28

1. Остановить API и фоновые обработчики R28. Не смешивать R28 и R29 в одной базе.
2. Сделать проверяемую резервную копию базы (см. `docs/BACKUP_AND_RESTORE_RU.md`).
3. Развернуть исходники R29 в отдельную папку и безопасно перенести переменные окружения вне Git и ZIP.
4. Выполнить Alembic `upgrade head` / `check` (новых R29 таблиц нет) и запустить обновлённые API и UI.
5. Проверить переписку: клиент отправляет новое сообщение, оператор открывает диалог, счётчик после подтверждения верен. Не использовать живые токены для локального теста.

## Не подтверждено

- Многосерверный прогон PostgreSQL и сквозные отправки с реальными социальными аккаунтами.
- Миграция основного UI на React 19 (npm registry недоступен, действует проверенный legacy React).
- Полный аудит безопасности, платёжная система, production-деплой, SLA реальных подключений.
