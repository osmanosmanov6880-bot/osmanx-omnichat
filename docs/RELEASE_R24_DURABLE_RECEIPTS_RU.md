# OSMANX OMNICHAT R24 — не терять квитанции WhatsApp

**Дата:** 5 ноября 2026 года. **Статус:** локально проверенный инженерный релиз ветки восстановления R19–R23. Не производственная эксплуатация.

## Зачем это бизнесу

WhatsApp может сообщить об отправке, доставке или прочтении ответа почти одновременно с тем, как наш фоновый обработчик сохраняет ответ API. В R23 вебхук пытался найти исходящее сообщение по внешнему ID немедленно и, если этого ID в базе ещё не было, пропускал событие навсегда. Поэтому настоящий ответ площадки мог остаться в интерфейсе со статусом «Принято API».

**R24 хранит подписанную квитанцию до сопоставления**, а затем автоматически уточняет статус исходящего ответа. В обычном интерфейсе никакая дополнительная кнопка не нужна.

## Что изменено в настоящем коде

1. **Новое хранилище `provider_delivery_receipts`.** SQL-таблица с составным ключом `(channel_id, external_message_id)` и обязательной организацией. Хранит только ID сообщения площадки, статус, контрольный отпечаток адресата и времена получения. **Текст сообщения, токен, имя и сырой номер телефона в таблицу не записываются**. Отпечаток — псевдоним, не абсолютная анонимизация.
2. **Атомарное обновление квитанций.** `INSERT … ON CONFLICT DO UPDATE` поддерживается в SQLite/PostgreSQL. Если события приходят не по порядку, `read` не снижается до `sent`, а `delivered` не превращается в `failed` из-за запоздалой квитанции. При проверке неверного адресата обновление блокируется.
3. **Двойная сверка на обеих сторонах.** После записи webhook и после успешной отправки ответом API выполняется отдельный проход сверки **после COMMIT**, перекрывающий гонку двух параллельных транзакций. Старая очередь с безопасными захватами и ручной сверкой неизвестных исходов сохранена.
4. **Изоляция компаний.** Квитанция относится к конкретному каналу организации. Если внешний ID неожиданно совпадает у двух переписок одного канала, система не гадает — обновление не выполняется. Квитанции с идентификатором чужого получателя не меняют диалог.
5. **Очистка и удаление рабочей области.** Временные записи старше 30 дней удаляются существующей периодической очисткой, а при удалении организации её записи удаляются **до каналов**, чтобы не возникало ошибок внешних ключей в PostgreSQL.
6. **Понятный экран.** Старые подписи «Принято API», «Отправлено», «Доставлено», «Прочитано» продолжают работать. «Контроль доставки» показывает нейтральный счётчик квитанций WhatsApp за последние 24 часа, **только по своей компании**. Это число может включать статусы `failed`; оно не является показателем успешно доставленных сообщений.

## Проверено

- **172/172 автоматических серверных теста**, пять отдельных процессов pytest: 65 + 41 + 30 + 25 + 11, каждый завершился кодом 0.
- 11 новых сценариев R24: квитанция до сохранения API ID, квитанция после; повторные/неупорядоченные статусы, исправление провайдерского `failed`, несовпадающий получатель, чужая организация, неправильная подпись, старые квитанции и очистка, параллельные upsert, удаление компании и миграция R23 → R24.
- SQLite `alembic upgrade head` + `alembic check` — успешно, ревизия **`f24000a10001`**, расхождений нет.
- Компиляция существующего TypeScript UI — успешна.
- Chromium с локальным FastAPI на **1512 × 950, 390 × 844, 320 × 700** — настоящий React UI, подписанные тестовые webhook-события и статус «Прочитано» без ошибок JavaScript или горизонтального переполнения. Скриншоты: `docs/preview-r24-whatsapp-receipts-*.png`.

## PostgreSQL и реальные соцсети

В GitHub Actions включён тест на **настоящем PostgreSQL 16**: две конкурентные SQL-сессии обрабатывают `sent` и `read`, проверяются итог `read` и защита адресата. **Этот workflow только подготовлен — локально PostgreSQL и Docker недоступны, подтверждения успешного CI ещё нет.**

**Реальная доставка WhatsApp/Instagram/Авито и других каналов не проверялась.** Нужны официальные аккаунты, доступные webhook-URL с HTTPS и согласованные тесты площадок. Одобренный провайдером `read` означает информацию от WhatsApp, не универсальную гарантию прочтения каждым человеком.

**React 19 пока не включён.** npm-реестр недоступен из среды сборки; проверенная версия интерфейса всё ещё использует React 16. Отдельный план обновления сохранён в `docs/REACT19_MIGRATION_RU.md`.

## Обновление с R23

1. Остановите R23 API и старые фоновые обработчики.
2. Сохраните и **проверьте** резервную копию текущей базы. Не делайте обновление без копии и плана отката.
3. Установите R24 отдельно и примените `PYTHONPATH=backend python -m alembic -c backend/alembic.ini upgrade head` на тестовой копии, затем на целевой базе в окно обслуживания.
4. Проверьте `alembic_version = f24000a10001` и права доступа к разделу «Контроль доставки».
5. После этого запускайте новые worker и API; **не смешивайте R23 и R24 с одной базой**.

**Не выполнялись:** публикация, реальные аккаунты, платежи, независимый security-аудит, промышленная нагрузка.
