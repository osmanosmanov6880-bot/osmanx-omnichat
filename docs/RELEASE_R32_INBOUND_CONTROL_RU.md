# OSMANX OMNICHAT R32 — четыре инженерных блока управления входящими

Дата: 5 ноября 2026. Версия **3.2.0-recovery**. Продолжение восстановленной ветки R19–R31. Это локальный инженерный релиз, не доказанный production-деплой.

## Блок 1. Управление инцидентами и изоляция компаний

Добавлены независимые паузы **обработки входящих** для всей организации и отдельного live-канала. Новые подписанные/авторизованные webhook продолжают проходить проверку и коммитятся в шифрованный `inbound_jobs`, однако worker не выдаёт новые захваты остановленной компании/каналу. Отдельная пауза канала не сбрасывается при возобновлении компании. Уже начатая до паузы обработка может корректно завершиться — это не отмена входящих событий.

- Структура: `organizations.inbound_paused_at/by/reason` и аналогичные поля `channel_connections`.
- API: `POST /api/operations/inbound/pause`, `POST /api/operations/inbound/resume`, с `scope=organization|channel`, `channel_id` для конкретного аккаунта и обязательной причиной. Только `owner/admin`.
- CAS в SQL отклоняет повторную или конфликтующую паузу (`HTTP 409`). Каждое действие протоколируется в `audit_logs`.
- Сохраняется запрет просмотра данных другой компании; неавторизованным операторам управление недоступно.

**Эксплуатационный предел:** несохранённые провайдером повторы нельзя считать гарантированными. При паузе более 14 дней техническая политика хранения очищает содержимое ожидающих событий. Требуется мониторить отставание и не держать паузу без контроля.

## Блок 2. Контроль заполнения защищённой очереди

Добавлен `INBOUND_MAX_PENDING_PER_CHANNEL`, по умолчанию **5000** событий с ещё сохранённым шифрованным содержимым в статусах `queued/retrying/processing/failed` для **каждого канала**. При достижении порога новое событие не коммитится и webhook получает **HTTP 503 + Retry-After: 30**, вместо ложного подтверждения приёма. Повтор уже зафиксированного события продолжает быть идемпотентным даже при полной очереди.

- На PostgreSQL запись серийно допускается под `SELECT ... FOR UPDATE` на строке канала, поэтому параллельные API-процессы видят общий предел.
- На локальной SQLite SQL-проверки и транзакционные записи подтверждены тестами. PostgreSQL-конкуренция добавлена в CI, но локально PostgreSQL не запущен.
- `HTTP 503` сигнализирует провайдеру о необходимости повторить событие; реальная политика повторов зависит от конкретной соцсети и её API, поэтому 100%-я гарантия повторной доставки не заявляется.
- Исполнение уже сохранённой очереди освобождает вместимость автоматически.

## Блок 3. Массовый возврат ошибочных входящих и постраничная история

- `GET /api/operations/inbound/triage` — фильтрация по статусу/каналу/провайдеру и устойчивый курсор `(created_at, id)`, лимит 1–100; организация обязательно применяется в SQL-запросе. Ответ содержит только технические поля без шифротекста, идентификаторов клиентов и токенов.
- `POST /api/operations/inbound/retry-batch` — повтор до **25** заданий одного канала по одному API-запросу (интерфейс использует порции по 20). Только `failed`, сохранённый шифротекст, возраст меньше 14 дней, `owner/admin`, обязательная причина, SQL CAS для каждого задания.
- Совместимость прежних маршрутов `/api/operations/inbound` и одиночного повтора сохранена. Одиночный повтор теперь также не разрешает событие старше срока хранения.
- Повтор входящего **не отправляет** ответ клиенту. Повторная запись того же сообщения исключается существующей идемпотентностью R30/R31.

## Блок 4. Интерфейс, миграции, CI и воспроизводимость

- Тёмный OBSIDIAN-интерфейс на русском: контролы уровня компании/канала, причины действия, предупреждение о приостановке, метрики отставания, фильтры и «Показать ещё», выбор канала и подтверждённое пакетное восстановление.
- Новая Alembic-миграция `f32000a10001_inbound_incident_controls.py` от R31; существующие события, каналы и переписки остаются без изменений.
- Тесты: `backend/tests/test_r32_inbound_operations.py` и браузер `scripts/browser_r32_inbound_control.py` на 1512, 390 и 320 px. Отдельный план проверки PostgreSQL четырьмя процессами: `scripts/verify_r32_postgres.py` в GitHub Actions.
- `scripts/verify_r32_migration.py` создает заполненную тестовую базу R31, применяет обновление, проверяет существующие строки и новую схему.
- `scripts/run_isolated_regression.py` прогоняет тесты по отдельным модулям с таймаутами, не заявляя успех по одним только точкам в выводе.

## Переход с R31

1. Остановите **все** API/worker R31. Не подключайте два несовместимых релиза к одной БД одновременно.
2. Создайте резервную копию и **проверьте возможность её восстановления**. Сохраните актуальные ключи `INTEGRATION_ENCRYPTION_KEY` и `INTEGRATION_ENCRYPTION_PREVIOUS_KEYS` отдельно от архива.
3. Распакуйте R32 в новую папку, перенесите свои настройки окружения **без загрузки секретов в ZIP**.
4. Выполните `alembic -c backend/alembic.ini upgrade head`, затем `alembic -c backend/alembic.ini check`.
5. Проверьте `INBOUND_MAX_PENDING_PER_CHANNEL` с учётом нагрузки и политики повторов конкретных провайдеров; начальное значение 5000.
6. Запустите API и worker, проверьте экран «Контроль доставки», пройдите контрольный входящий webhook и оцените длину очереди.

**Границы подтверждения:** все серверные и браузерные тесты используют локальные тестовые данные. Постгрес-гонки подготовлены для CI, не проверены в текущем окружении. React 19 остается отдельным opt-in-кандидатом; рабочий runtime — legacy. Реальная соцсеть, публикация, оплата и продакшен-развёртывание не выполнялись.
