# OSMANX OMNICHAT R30 — безопасное первое обращение

Дата: 5 ноября 2026 года. **Локальная инженерная сборка; не production**. Продолжает восстановленную ветку R19–R29.

## Какая ошибка устранена

R29 исправил атомарное увеличение непрочитанных **у существующей переписки**, но при самом первом входящем несколько webhook-процессов могли одновременно решить, что контакт и диалог отсутствуют. Затем один из них получал нарушение уникальности `contact_identities(channel_id, external_user_id)` либо `conversations(channel_id, external_chat_id)`. Повторная доставка webhook могла повторить действие, но это не надёжное разрешение гонки.

В R30 `ingest_inbound` использует транзакционные `INSERT ... ON CONFLICT DO NOTHING` с существующими уникальными индексами **SQLite и PostgreSQL**. Каждый вызов:

1. Ищет уже созданный диалог внутри организации и канала.
2. При отсутствии сначала претендует на уникальную идентичность клиента. Если другой процесс выиграл, удаляет только свою временно созданную карточку и загружает существующую.
3. Создаёт диалог с атомарной проверкой уникального внешнего chat ID. При конфликте удаляет свою ещё не нужную идентичность/карточку и использует настоящий диалог победителя.
4. Создаёт входящее сообщение через уникальную пару `(conversation_id, external_id)`. Повтор того же ID возвращает существующее сообщение, не меняя счётчики.
5. **Только после успешной записи нового сообщения** атомарно увеличивает число непрочитанных и версию диалога по правилам R29. Правила автоматизации не срабатывают второй раз на копию сообщения.

Все операции остаются в одной транзакции вызывающего webhook/синхронизации. Ошибка до commit откатывает новые сущности; нет промежуточного состояния, которое считалось бы завершённым диалогом.

## Дополнительные исправления

- При создании нового диалога время последнего сообщения берётся из **проверенного времени события**, а не из времени обработки; запоздавшее первое сообщение не выглядит новым событием текущего момента.
- Некорректные времена (`NaN`, бесконечности, нечисловые значения, недопустимые даты) заменяются временем получения, чтобы не портить сортировку Inbox.
- Подписанные callbacks Telegram, VK и MAX проверяют форму вложенных JSON-объектов; повреждённые данные дают HTTP 422, а не случайный HTTP 500. Слишком большой или некорректный список вложений MAX отклоняется.
- Сломанное поле timestamp MAX обрабатывается безопасно.
- Действия не создают новые внешние подключения и **не отправляют сообщения в соцсети**.

## Гарантии, которые нельзя преувеличивать

- SQLite/PG SQL-ограничения исключают сохранение двух диалогов с одинаковым `channel_id + external_chat_id`. Подтверждение at-most-once в БД **не означает**, что все внешние провайдеры гарантированно пришлют каждое событие: надёжность зависит также от их политики повторов и доступности инфраструктуры.
- В настоящей многосерверной инсталляции PostgreSQL отдельно проверяют `scripts/verify_r30_postgres.py`: четыре параллельных первых события, повтор одного ID и два отправителя одной беседы. Скрипт включён в CI, **в данной локальной среде PostgreSQL отсутствует**.
- Приложение по-прежнему работает в проверенном legacy React runtime. React 19/Vite запланирован, но не является активным проверенным UI в R30.

## Обновление R29 → R30

1. Остановите все фоновые обработчики и HTTP API прежней версии.
2. Создайте и проверьте резервную копию базы. Инструкция: `docs/BACKUP_AND_RESTORE_RU.md`.
3. Разверните исходники R30 отдельно; конфигурацию и секреты храните вне ZIP/Git.
4. Проверьте `alembic upgrade head` и `alembic check`. Новых миграций R30 нет, используются прежние уникальные индексы.
5. Запустите R30 API/UI одновременно и проверьте первый входящий на **своём разрешённом тестовом** подключении. Не смешивайте разные версии workers на одной базе.
