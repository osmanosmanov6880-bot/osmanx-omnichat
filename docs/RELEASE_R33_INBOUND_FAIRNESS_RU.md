# OSMANX OMNICHAT R33 — четыре крупных инженерных блока

Дата: 5 ноября 2026. Версия **3.3.0-recovery**. Продолжение восстановленной ветки R19–R32, **локальный инженерный релиз**, не подтверждённое production-развёртывание.

## 1. Справедливое распределение входящих между аккаунтами

R32 выбирал старейшие готовые события; тысячи старых сообщений одного канала могли вытеснять более свежие события других компаний. R33 формирует SQL-ранг события внутри каждого канала `row_number() over (partition by channel_id order by created_at,id)`. Планировщик сначала берёт по одному сообщению на канал, затем по второму, и так далее. Если размер batch=1, приоритет помогает поддерживать `channel_connections.inbound_last_dispatched_at`, который обновляется **только после атомарного успешного захвата**. Существующие роли, паузы компании/канала, уникальные ID сообщений и ограничение числа попыток сохранены.

SQL-логика рассчитана на SQLite и PostgreSQL. Тесты двух соединений SQLite пройдены, четырёхпроцессный PostgreSQL-сценарий добавлен в CI и **не запускался локально**. Это улучшение справедливости, но не гарантия фиксированного времени доставки при перегрузке или сбое внешнего провайдера.

## 2. Необратимое закрытие проблемного входящего

`POST /api/operations/inbound/{job_id}/dismiss` разрешён только `owner/admin`. Запрашивает категорию закрытия, причину длиной от 12 символов и `confirm_permanent_loss=true`; проверяет принадлежность организации и статус `failed`. SQL compare-and-set позволяет только одно окончательное решение в конкурирующих запросах.

Успех атомарно меняет статус на `dismissed`, **удаляет `encrypted_event`**, сохраняет `dismissed_at/by/code` и запись в `audit_logs`. Неизвестный статус, повторное закрытие, несогласованная роль или чужое событие блокируются. Само событие больше нельзя вернуть кнопкой повтора, клиентская переписка не меняется и исходящий ответ не отправляется. Повтор доставленного площадкой старого webhook остаётся идемпотентно распознанной копией закрытого события; перед закрытием обязательно подтвердите, что восстановление действительно не требуется. Технические метаданные удаляются по существующей политике через 30 дней.

## 3. Диагностика нагрузки и задержек по каналам

`GET /api/operations/inbound/health?limit=50` (максимум 100) доступен `owner/admin/lead`, возвращает только разрешённые метаданные своей компании: число ожидающих, повторяемых и ошибочных событий; время ожидания старейшего, лимит на канал, процент заполнения, пауза и сигнал риска.

Сигналы: критично — ошибка, заполнение >=90% или ожидание >=30 минут; предупреждение — заполнение >=60% или ожидание >=10 минут. Это **пороговые диагностические сигналы, не SLA провайдера**. Нет клиентских текстов, внешних user ID, токенов, шифротекста, названий чужих компаний или чужих аккаунтов. Результат ограничен и отсортирован по риску.

## 4. Русский OBSIDIAN-интерфейс, эксплуатация и проверки

Раздел «Контроль доставки»: карточки здоровья аккаунтов, фильтр «Закрыты», причина и двойное подтверждение необратимого удаления, счетчик закрытых событий, подсказки и результат действия. Полный путь протестирован в настоящем Chromium на ПК 1512px, телефонах 390px и 320px. Frontend скомпилирован TypeScript; проверка старого экрана R32 пройдена.

Новая миграция Alembic `f33000a10001_inbound_fairness_and_disposition.py` добавляет поле канала, три поля disposition и индекс выборки. `scripts/verify_r33_migration.py` подтвердил сохранение существующей организации, канала и ожидающего encrypted payload R32. Обновлены тесты, браузерный сценарий, CI и русская документация.

### Установка и ограничения

Остановите все R32 API и worker, сохраните проверенный бэкап и ключи шифрования, установите R33 и выполните `alembic -c backend/alembic.ini upgrade head`, затем `alembic -c backend/alembic.ini check`. Не подключайте разные версии к одной БД. Сервис по умолчанию локальный, **не** production.

В текущей среде **не проверены** реальная многопроцессная PostgreSQL-гонка, живые API соцсетей, production-публикация, реальные платежи и переход рабочего React runtime на React 19. CI содержит подготовленные PostgreSQL и браузерные сценарии, **успех GitHub Actions не заявляется**, если они ещё не запускались на GitHub.
