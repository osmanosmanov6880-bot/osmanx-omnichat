# OSMANX OMNICHAT R31 — защищённая очередь входящих событий

Дата: 5 ноября 2026. Версия: **3.1.0-recovery**. Это **локальная инженерная сборка**, не подтверждённая production-версия. Продолжение восстановленной ветки R19–R30.

В этом проходе выполнены **четыре связанные реализации в настоящем коде**, а не только изменения интерфейса.

## Блок 1. Подтверждение webhook только после надёжной записи

Telegram, VK, MAX, WhatsApp, Instagram и Facebook Messenger сначала проходят предусмотренные для них проверки секрета/подписи и формата данных. Для каждого входящего сообщения затем создаётся запись `inbound_jobs` в SQL-БД с уникальной парой `(channel_id, fingerprint)`. Содержимое **нормализовано и зашифровано** текущим `INTEGRATION_ENCRYPTION_KEY` (Fernet/MultiFernet). Текст сообщения, контактные ID и вложения не хранятся в открытом виде в очереди.

Строки очереди коммитятся **до ответа на webhook**. Если база не смогла принять событие, успешный ответ провайдеру не выдаётся. Если событие уже есть, счётчик дублей увеличивается атомарно; повторная доставка не создаёт новое сообщение.

После записи API пытается сразу обработать сообщение для обычного поведения Inbox. Если обработка упала, HTTP-приём уже подтверждён благодаря записи в журнале, и обработку продолжает фоновый worker.

Важно: `accepted` в ответе API — число **немедленно обработанных новых сообщений**, а не всех сообщений, сохранённых на будущую обработку. Клиентская переписка создаётся только при успешной обработке.

## Блок 2. Аварийное восстановление и устранение дублей

Новый `backend/app/inbound_jobs.py` реализует SQL-claim с `claim_token`, ограниченным сроком захвата и атомарной фиксацией результата вместе с записью клиента, переписки, сообщения и idempotency receipt. Старый процесс не может завершить чужой захват. Потерянный захват восстанавливается автоматически; результат проверяется по уникальным ID сообщений.

Повторы после ошибок идут с возрастающей задержкой, максимум **5 попыток**. После исчерпания лимита либо потери пятого захвата запись помечается `failed`, не исчезает и не создаёт бесконечный цикл. До повторной попытки причина ошибки фиксируется **кодом класса исключения**, без приватных текстов из webhook.

В production допускаются несколько API и worker-процессов, но **реальная проверка многопроцессности на PostgreSQL отдельно подготовлена для CI и в текущей среде не выполнялась**. Локальные гарантии SQLite не заменяют испытания PostgreSQL.

## Блок 3. Операционный контроль и ручной возврат

В разделе **«Контроль доставки»** появилась секция **«Приём обращений»** с числом обработанных событий, ожидающих, требующих проверки и дублей за последние 24 часа. Список ограничен 100 событиями на сервере и показывает только тип площадки, статус, время, количество попыток и технический код ошибки — **никаких текстов клиентов или токенов**.

`GET /api/operations/inbound` доступен ролям owner/admin/lead, возвращает только записи своей организации. `POST /api/operations/inbound/{id}/retry` доступен только owner/admin, требует записать объяснение (8–300 символов), атомарно проверяет статус `failed`, оставляет запись в `audit_logs`. Повтор возвращает входящее событие **на обработку в системе**; это **не** повторная отправка сообщения клиенту.

Интерфейс на русском, проверен в настоящем Chromium на ширине 1512, 390 и 320 px. Модальное окно, сохранение причины и обновление статуса прошли end-to-end c синтетическим событием.

## Блок 4. Сроки хранения, изоляция компаний, миграции и QA

- После успешного сохранения переписки `encrypted_event` немедленно становится `NULL`.
- Необработанное зашифрованное содержимое, если событие старше **14 суток**, удаляется и событие переходит в `expired`.
- Метаданные `done/expired` старше **30 суток** удаляются пакетами, чтобы не накапливать технический журнал бесконечно.
- Удаление рабочей области удаляет все связанные `inbound_jobs` **до** удаления каналов и компании.
- Действия с чужой организацией отклоняются, а роль lead не может вручную запускать повтор.
- Миграция Alembic `f31000a10001` добавляет таблицу и индексы. Старые сообщения и компании сохраняются, существующие webhook receipts не перезаписываются.
- Отдельная CI-проверка запускает четыре независимых процесса PostgreSQL для одновременного сохранения одного события и четыре процесса для конкурентного claim; **локально её не было**.

## Как обновиться с R30

1. **Остановите старые API и фоновые обработчики R30**. Не смешивайте версии workers на одной БД.
2. Сделайте и **проверьте** резервную копию БД по `docs/BACKUP_AND_RESTORE_RU.md`.
3. Разверните архив R31 в отдельную папку. Файлы конфигурации и ключи шифрования не включены; используйте существующие переменные окружения.
4. **Не теряйте старые `INTEGRATION_ENCRYPTION_PREVIOUS_KEYS`**, пока в новой зашифрованной входящей очереди есть непрочитанные события со старым ключом.
5. Примените `alembic -c backend/alembic.ini upgrade head`, затем `alembic -c backend/alembic.ini check`.
6. Запустите API и выделенный worker, проверьте «Контроль доставки» и входящее событие на своём разрешённом тестовом аккаунте.

## Подтверждённые проверки

Полная проверка и точное число тестов см. в `docs/QA_R31_RU.md`. На локальной SQLite-проверке отдельные новые тесты подтверждают создание зашифрованной очереди, сбой с последующим восстановлением, защиту от дублей старых релизов, пять попыток, ручной возврат с аудитом, защиту чужих компаний и удаление данных по сроку хранения. Проверены миграция R30→R31 и код TypeScript. Подробности ограничений — в QA.

**Не подтверждены** в этой среде: PostgreSQL с несколькими реальными серверами, полноценная доставка через официальные внешние API, React 19 как активная сборка, физические мобильные устройства и независимый security-аудит. Публикация, платежи и настоящие аккаунты не затрагивались.
