# OSMANX OMNICHAT v1.5 — Safe Recovery

**Дата:** 4 ноября 2026 года. **Статус:** локальный MVP; публичная эксплуатация не аттестована.

## Что действительно изменено

### 1. Безопасное резервное копирование SQLite

Добавлен `scripts/backup_safety.py`. При создании локальной копии используется встроенный механизм SQLite Backup API, а не простое копирование работающего файла `.db`. Это важно при активном журнале WAL.

Каждая копия получает:
- проверку `PRAGMA integrity_check`;
- контрольную сумму SHA-256, размер и манифест JSON;
- права доступа только владельцу файла в POSIX;
- атомарную публикацию после успешной проверки;
- возможность восстановления **только в новый файл**, без перезаписи рабочей базы.

Начиная с v1.5, `start_windows.bat` и `start_linux.sh` перед локальной миграцией проверяют текущую ревизию базы. Если ревизия устарела, сначала создаётся резервная копия. Если копию получить нельзя, запуск миграции прерывается. Если миграция не нужна, лишняя копия не создаётся.

### 2. Исправлен опасный сценарий резервирования PostgreSQL

Старый `infra/backup-postgres.sh` использовал конвейер `pg_dump | gzip`. Ошибка `pg_dump` могла оставить непустой `.gz`, который ошибочно воспринимался как успешная копия.

Теперь PostgreSQL-архив формируется в **custom format**, код завершения `pg_dump` проверяется напрямую, затем запускается `pg_restore -l` для проверки структуры. При сбое временный файл удаляется. Успешная копия сопровождается SHA-256-манифестом.

**Ограничение:** `pg_restore -l` подтверждает возможность прочитать структуру архива, **но не заменяет пробное восстановление в отдельную базу**. Docker и PostgreSQL в текущей среде отсутствуют. Поведение команд проверено только автоматическими тестами с имитацией внешних процессов. Проверка настоящего восстановления остаётся обязательной перед production.

### 3. Сборка релиза не забирает базы пользователей

`build_release.py` теперь исключает папку `backups`, файлы `.dump`, `.backup`, `.sql`, `.gz`, SQLite-базы и `.env`. Добавлен автоматический тест, который кладёт случайный секрет в папку резервных копий, собирает архив и подтверждает, что секрет не попал в релиз.

### 4. Технический долг

Проверенная пользовательская сборка всё ещё использует **React 16**. Файлы перехода на React 19 оставлены как отдельная экспериментальная ветка. В этой среде npm-реестр возвращает `EAI_AGAIN`, поэтому считать миграцию завершённой нельзя.

## Проверенные сценарии

- Снимок активной SQLite-базы с WAL и восстановление в новый файл.
- Определение изменения контрольной суммы после повреждения резервной копии.
- Запрет перезаписи действующей базы.
- Отказ от копирования отсутствующей или неподходящей базы.
- Имитация сбоя `pg_dump`: частичный файл не публикуется.
- Имитация отклонения архива `pg_restore`: частичный файл не публикуется.
- Защита ZIP-релиза от включения резервных копий.
- Автоматическое копирование перед миграцией только при изменении ревизии.
- Сквозная локальная проверка на базе после Alembic: копия и восстановление сохранили 26 таблиц и ревизию `ee4a14b80001`.

## Использование

**Локальная Windows:** `backup_local_windows.bat` в корне проекта.

**Локальная Linux/macOS:** `./backup_local_linux.sh`.

**Проверить копию SQLite:**

```bash
python scripts/backup_safety.py sqlite-verify --file backups/ИМЯ_КОПИИ.sqlite3
```

**Восстановить в новый файл для проверки:**

```bash
python scripts/backup_safety.py sqlite-restore-new --file backups/ИМЯ_КОПИИ.sqlite3 --target recovery-check.db
```

**PostgreSQL в Docker:**

```bash
./infra/backup-postgres.sh
python scripts/backup_safety.py postgres-verify --file backups/ИМЯ_КОПИИ.dump
```

**Важно:** копии содержат данные клиентов. Храните их в зашифрованном хранилище, вне сервера; настройте срок хранения и регулярно проверяйте восстановление. Хеш SHA-256 обнаруживает случайные изменения, но не заменяет цифровую подпись и защиту от умышленной подмены манифеста.

Публикация, платежи и реальные аккаунты соцсетей не затрагивались.
