# OSMANX OMNICHAT v1.2 — Reliability & Clarity

**Статус:** локальная self-hosted сборка для разработки и проверки рабочих сценариев. Публикация, оплаты и подключение реальных клиентов не запускались. Не означает готовность к промышленной эксплуатации.

## Инженерные изменения

### 1. Атомарная дедупликация событий

- `backend/app/webhooks.py`: `reserve_event` регистрирует событие в PostgreSQL/SQLite через `INSERT ... ON CONFLICT DO NOTHING` и уникальный ключ `(provider, fingerprint)`.
- Ранее проверка `SELECT`, а затем `INSERT` могла завершиться конфликтом, если событие одновременно обрабатывали два сервера. Теперь резервирование атомарно.
- Резервирование включено в одну транзакцию с сохранением сообщения: при ошибке обработки транзакция откатывается, и площадка может повторить webhook.
- Применено к WhatsApp, Instagram, Messenger, Telegram, ВКонтакте и MAX. Никакой обход ограничений официальных API не добавлялся.

### 2. Запрет межорганизационной отправки

- `backend/app/services.py`: перед вызовом внешнего адаптера исходящая очередь строго сравнивает компанию, сообщение, диалог и канал.
- При повреждённой или неправильно сформированной записи отправка блокируется, а чужое сообщение и его статус не изменяются.
- Это дополнительная защита в глубину, помимо API RBAC и tenant-scoped запросов.

### 3. Аналитика и мониторинг без загрузки истории целиком

- `analytics()` вычисляет число обращений, статусы, нагрузку, первые ответы, SLA и выручку через SQL-агрегации.
- Для семидневного графика используются только метки времени входящих сообщений за соответствующие семь календарных дней в часовом поясе компании.
- Список каналов в `/api/operations/overview` ограничен 200 записями с признаком усечения; **общие счётчики считают все записи**, а не только показанные.
- `no_response` теперь определяется по последнему сообщению по времени, а не по случайному порядку выдачи SQL.
- Для крупных инсталляций всё ещё нужны отдельные индексы, нагрузочные испытания и дальнейшая оптимизация выборок.

### 4. Очередь доставки — проблемы видны первыми

- `/api/operations/outbox` сортирует в первую очередь `uncertain`, затем `failed` и остальные статусы, чтобы оператор не потерял ошибку среди сотен успешных отправок.
- В разделе «Контроль доставки» появилась одна понятная подсказка «Что сделать сейчас», а технические названия статусов заменены русскими.
- Операция ручной сверки **не** отправляет сообщение повторно, а требует доказательство проверки в исходной соцсети.

## Проверка

- Новые тесты `backend/tests/test_v12_resilience.py`: уникальность event receipts, rollback, повторные Meta события, изоляция компаний при ошибочной записи очереди, SQL-агрегаты, параллельное резервирование webhook, первоочередные неопределённые отправки и два worker-процесса, не дублирующие ответ (в моделируемой среде).
- Полный Python-набор: см. `pytest -q backend/tests` и файл `docs/VERIFICATION_V12.txt` после финального прогона.
- React/TypeScript: компиляция `tsc --project frontend/tsconfig.json`.
- Chromium: `PYTHONPATH=backend python scripts/browser_v12_operations.py` — ПК 1512 px, телефоны 390 и 320 px. Проверяется реальный React UI с настоящим FastAPI TestClient в качестве локального транспорта, **не** реальный HTTPS-хостинг.
- Alembic: `upgrade head`, `check` без расхождений. **Структура таблиц в v1.2 не менялась**, отдельная миграция не требуется.

## Ограничения и остаточные риски

1. Старый React 16 **не обновлён**: в текущей среде недоступен npm-реестр. Перед production потребуется воспроизводимая сборка на поддерживаемом React, тесты и обновлённые зависимости. Исходный код не выдаётся за React 19.
2. Новые конкурентные тесты выполнены на SQLite. Не проверены реальные PostgreSQL под нагрузкой, Redis, Docker или несколько изолированных серверов с независимой сетью.
3. Никакие реальные разрешённые аккаунты социальных сетей в тестах не использовались. Пройдены контрактные и локальные проверки; фактическая доставка через Meta, Авито, Telegram, ВКонтакте, MAX требует настроенных аккаунтов, одобрений и HTTPS.
4. Публикация, биллинг, сбор платежей и включение коммерческого SaaS не выполнялись по просьбе владельца.

## Запуск и обновление

Windows: распаковать ZIP, выполнить `start_windows.bat`, открыть `http://127.0.0.1:8000`. Linux/macOS: `./start_linux.sh`.

Для продолжения работы со **своими** данными сохранить старые `.env` и БД отдельно: архив не содержит секретов и пользовательской базы. Сделать резервную копию БД, затем запустить `alembic -c backend/alembic.ini upgrade head` (с верным `DATABASE_URL`). Не заменять рабочую БД демоданными.

Подробнее: [Сверка доставки — короткая инструкция](OPERATIONS_RUNBOOK_V12.md).
