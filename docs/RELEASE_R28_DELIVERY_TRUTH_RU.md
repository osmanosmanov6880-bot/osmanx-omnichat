# OSMANX OMNICHAT R28 — честная аналитика доставки и SLA

**Релиз:** 5 ноября 2026 года. **Основа:** R27 Sender Serialization. **Статус:** локальная инженерная сборка; не публичный production-сервис.

## Проблема, которую устранили

В R27 нажатие «Отправить» создаёт исходящее сообщение и ставит его в очередь. До принятия внешним API оно могло иметь статус `queued`, `failed` или `uncertain`, но старые отчёты считали само наличие исходящего сообщения достаточным ответом клиенту. Из-за этого могли занижаться количество необработанных диалогов и просрочки SLA.

## Новая модель ответа

1. **Очередь, обработка, ошибка, неизвестный результат, отмена** — не подтверждённый ответ.
2. **Ответ принят официальным API (2xx)** — подтверждается в транзакции фиксации отправки. Новое поле `messages.response_confirmed_at` содержит время принятия, а не создания текста.
3. **Собственный чат сайта** — статус `accepted` означает «сохранено на сервере». Только аутентифицированная квитанция от виджета, отправленная после показа сообщения, переводит запись в `delivered` и фиксирует момент подтверждения.
4. **Подписанный WhatsApp webhook** — при сопоставлении с исходящим сообщением подтверждение `sent/delivered/read` сохраняет время первой достоверной квитанции. Повторные квитанции не сдвигают первоначальное время.
5. **Демонстрационные ответы** — маркируются как demo и получают собственное время ответа; это не считается испытанием реального провайдера.

Вычисления **«Просрочено по SLA»**, **«Без ответа»** в аналитике и **«Центре управления»** используют общий SQL-предикат подтверждённого исходящего (`backend/app/delivery_truth.py`). Важна не только подтверждённая запись, но и то, что **ответ был создан после последнего входящего сообщения**. Новое обращение не скрывается прежним ответом.

## Для владельца: что появилось

- «**Ожидают подтверждённого ответа**»: число диалогов, где последнее обращение клиента ещё не получило подтверждённого ответа.
- «**Исходящих в очереди или обработке**»: сообщения, не закончившие отправку в API.
- «**Нуждаются в проверке**»: ошибочные и неопределённые отправки. Последние нельзя автоматически повторять без сверки во внешней площадке.
- «**Принятие ответа**»: среднее время от первого входящего сообщения до первого зафиксированного подтверждения (API / виджет). Это **не** время прочтения клиентом.

**О старых сообщениях:** R28 не заполняет для них `response_confirmed_at` из `created_at`: это выдало бы создание черновика за подтверждение API. Предыдущие `sent/delivered/read` учитываются по их подтверждённым статусам для списка необработанных, но **не включаются** в новую среднюю длительность без точного времени подтверждения. Старые `accepted` без подтверждения в новой схеме консервативно остаются неподтверждёнными для SLA до явной сверки. Эта особенность R27→R28 задокументирована намеренно.

**Ручная сверка:** перевести `uncertain` в `accepted` можно только с записанным доказательством; это снимает текущий статус ожидания. Однако R28 не придумывает исторический момент автоматического API-подтверждения для такой операции, поэтому новое среднее время на этом событии не строится.

## Что изменено в коде

- `backend/app/delivery_truth.py` — общий SQL-предикат ответов.
- `backend/app/services.py` — получение подтверждённого времени API, аналитические SQL-агрегаты и проверка SLA.
- `backend/app/extras.py` / `backend/app/command.py` — единая семантика уведомлений и центра управления.
- `backend/app/website.py` / `backend/app/provider_receipts.py` — подтверждения от собственного виджета и подписанного webhook.
- `backend/app/fixtures.py` / `backend/app/synchronizers.py` — отдельная обработка демо и официально синхронизированных сообщений.
- `backend/alembic/versions/f28000a10001_verified_response_times.py` — совместимая миграция.
- `frontend/src/app.tsx` и собранный `frontend/public/app.js` — понятные русские подписи, без новых перегруженных экранов.
- `backend/tests/test_r28_delivery_truth.py` — 12 сценариев.
- `scripts/browser_r28_delivery_truth.py` — Chromium с реальным React и локальным FastAPI на 1512/390/320 px.
- `scripts/verify_r28_postgres.py` — отдельный проверочный скрипт, предназначенный для CI PostgreSQL 16.

## Как обновить R27 → R28

1. Остановить все экземпляры API и фоновые обработчики R27. Не запускать R27 и R28 одновременно на одной базе.
2. Создать резервную копию базы штатным инструментом и **проверить восстановление** копии на отдельной базе.
3. Распаковать R28 в **новую папку**. Перенести конфигурацию и секреты только через защищённые переменные окружения, не копировать `.env` в Git/ZIP.
4. Применить `alembic -c backend/alembic.ini upgrade head` с вашим `DATABASE_URL` и затем `alembic -c backend/alembic.ini check`.
5. Запустить `start_windows.bat` для локальной Windows-среды либо штатный безопасный startup в другой среде. Открыть `http://127.0.0.1:8000`.
6. Сравнить контроль доставки и отчёт аналитики на тестовой компании. Не включать реальную отправку до проверки прав, токенов, webhook и резервного восстановления.

**Не входит в этот релиз:** реальный публичный деплой, платежи, подключение/испытания реальных соцсетей, React 19 и подтверждённые здесь нагрузочные испытания на PostgreSQL. React 19/Vite остаются **кандидатом**, npm-реестр ранее был недоступен в рабочем окружении.
