# OSMANX OMNICHAT R21 — совместная работа без перезаписи изменений

**Дата:** 5 ноября 2026. **Статус:** локальная инженерная версия поверх восстановленной R19/R20. Это не подтверждённый production SaaS. Публикация, биллинг и реальные социальные аккаунты не изменялись.

## Что улучшено

### 1. Несколько сотрудников могут работать с одним диалогом

Раньше команды **«Изменить статус»**, **«Закрепить»** и **«Назначить ответственного»** читали старое значение объекта, затем записывали новый объект. При конкуренции сотрудников устаревшая команда могла незаметно затереть изменение коллеги.

Теперь каждая операция использует **один атомарный SQL `UPDATE`**, проверяющий организацию и ожидаемую версию диалога. При изменении версии другой командой приложение возвращает HTTP 409. Пользовательский интерфейс **автоматически загружает свежие данные и показывает понятное предупреждение**, а не заявляет о сохранении устаревшего действия.

Защита распространяется на операторские действия в реальном React UI. Дополнительный SQL-предикат `assigned_user_id` блокирует действие сотрудника, если назначение было отозвано между проверкой права и записью. **Назначение другого оператора в диалог с активной блокировкой ответа запрещено** до освобождения/истечения блокировки.

Существующие старые API-клиенты могут не присылать `expected_version`: им обеспечена атомарность SQL-операций и проверка принадлежности назначенного сотрудника, но полноценная защита от устаревшего клиентского состояния требует передать версию. Официальный фронтенд R21 **всегда** её передаёт.

Внутренние заметки, исходящие ответы и загрузка истории продолжают работать. Для исходящих ответов существующая проверка версии и дедупликация `client_nonce` не изменялись.

### 2. Интерфейс: конфликт — это действие, а не загадочная ошибка

При изменении диалога другим сотрудником R21 показывает: **«Коллега изменил диалог. Данные обновлены — проверьте их и повторите действие»**. Статус или назначение на экране обновляются до актуального состояния, незавершённая операция не выполняется автоматически.

### 3. Подготовлена PostgreSQL-проверка двух одновременных записей

`scripts/verify_r21_postgres.py` запускается **только** против одноразовой базы `omnichat_ci`, создаёт свою компанию и диалог, одновременно обновляет его двумя SQL-сессиями и проверяет, что версия увеличилась один раз. Задача подключена к GitHub Actions `postgres-migrations`. В данном локальном окружении PostgreSQL/Docker не запускались: **фактическое прохождение этого CI-теста пока не подтверждено**.

## Что проверено

- 6 новых серверных тестов: stale status/pin, atomic pin legacy mode, устаревшее назначение, блокировка во время ответа, сравнение версий двух SQL-сессий, валидация входных данных.
- Полный набор: **136 из 136 тестов прошли в двух отдельных процессах**: 111 тестов основного API и 25 тестов резервирования, веб-чата и WhatsApp. При едином запуске pytest также напечатал `136 passed`, но иногда процесс задерживается после отчёта из-за оставшихся потоков. В CI обе группы выполняются отдельными командами с обязательным кодом завершения 0; причину задержки единого pytest-процесса ещё нужно исследовать.
- TypeScript — `tsc --project frontend/tsconfig.json`, успешная компиляция.
- Alembic — `upgrade head`, `check`: нет расхождений. **Новую миграцию не потребовалось создавать:** версия R21 изменяет логику запросов, а не таблицы.
- Chromium: `scripts/browser_r21_team_conflicts.py` — реальный React UI, локальный FastAPI TestClient, одновременная имитация изменения коллеги, получение HTTP 409 и успешный повтор после обновления. Проверены разрешения **1512, 390 и 320 px**; нет ошибок JS и горизонтального переполнения.

## Ограничения

Рабочий интерфейс пока использует React 16. Подготовленная React 19/Vite сборка **не активирована**: npm-реестр недоступен в среде разработки. Настоящие социальные аккаунты не подключались и не тестировались; не проводились нагрузочные испытания PostgreSQL, независимый аудит безопасности или выпуск приложения в production.

## Обновление

1. Создать резервную копию базы и проверить её.
2. Распаковать проект R21 отдельно от действующего экземпляра и сравнить окружение.
3. На локальном проекте: Windows `start_windows.bat`; Linux/macOS `./start_linux.sh`. Для отдельного production PostgreSQL — применять существующую схему Alembic до запуска API, хотя новых таблиц в R21 нет.
4. Проверить два браузера с разными сотрудниками: открыть один диалог, сменить статус в первом и попробовать обновить старое состояние во втором. Второй должен получить предупреждение и свежие данные.

**Важно:** R21 продолжает восстановленную ветку R19/R20, а не исходную недоступную v1.8. Не заменяйте действующий сервер неизвестной версии без сравнения миграций и резервной копии.
