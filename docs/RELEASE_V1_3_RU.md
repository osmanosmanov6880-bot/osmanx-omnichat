# OSMANX OMNICHAT v1.3 — Shared Core & Fair Queue

**Релиз:** 4 ноября 2026 г.  
**Статус:** проверенный локальный MVP, НЕ готовая к коммерческой эксплуатации production-SaaS-система.

## Что изменено в исполняемом коде

### Общие ограничения публичных запросов

Раньше лимиты регистрации и создания демокомпаний хранились в памяти процесса. После перезапуска или при нескольких API-серверах их можно было обойти. Теперь регистрация, создание демоверсии и выдача новой сессии веб-чата используют **атомарный SQL-счётчик** с временным окном, работающий на SQLite и PostgreSQL.

- Счётчик хранится в `public_rate_buckets` (новая миграция `b1390a1e0001`).
- Клиентский IP не записывается в чистом виде: используется HMAC с ключом из окружения. Для production обязателен секрет.
- При превышении возвращается HTTP 429 и `Retry-After`.
- Старые счётчики удаляются обслуживающим worker'ом.
- Поддельный `X-Forwarded-For` игнорируется, если запрос не пришёл от явно доверенного прокси.

Это защита от базового злоупотребления, а не от всех возможных распределённых DDoS-атак; для публичного SaaS дополнительно необходима защита на edge.

### Справедливая SQL-очередь сообщений

Раньше `process_outbox` выбирал первые N самых старых ответов **по всей платформе**. Компания с большим потоком могла занять целую пачку, задержав ответы остальных. Теперь SQL использует `row_number() over (partition by organization_id ...)` и выбирает задания по уровню очереди внутри каждой компании. Затем каждое задание атомарно переводится из `queued` в `processing`.

- Тест: при 8 ожидающих ответах организации A и 1 ответе организации B, обработка двух заданий выбирает **по одному** для каждой организации.
- Сохранена защита от одновременной отправки одного задания разными обработчиками.
- **Неопределённые результаты после сетевого сбоя не отправляются повторно автоматически**: нужна сверка у провайдера.
- Устаревшие зависшие задания обрабатываются ограниченными пакетами по 300, чтобы worker не загружал неограниченный список в память.

SQL-справедливость не гарантирует одинаковое время доставки при сбоях провайдеров, их rate limits и большом количестве клиентов; нагрузочные тесты в PostgreSQL остаются обязательными.

### Production startup gate

Производственный API больше не должен молча создавать отсутствующие таблицы через `create_all()`: он **проверяет применённую версию Alembic** перед запуском. Если база пустая или миграции отстают, сервер выдаст понятную ошибку и не начнёт обслуживание с неправильной схемой.

Новые таблицы и индексы применяются командой:

```bash
PYTHONPATH=backend alembic -c backend/alembic.ini upgrade head
```

### CI и инфраструктура

В GitHub Actions добавлена отдельная задача `postgres-migrations` с эфемерным **PostgreSQL 16**: миграции, `alembic check`, проверка версии схемы и ключевых индексов. Это подготовленная проверка для CI; **в среде сборки Docker/PostgreSQL не запускались**. Поэтому результат прохождения этой задачи пока не заявляется.

## Что делать владельцу

1. Для локального демо: распаковать архив, запустить `start_windows.bat` или `./start_linux.sh` и открыть `http://127.0.0.1:8000`.
2. Для обновления старой установленной копии: **сделать резервную копию базы**, заменить файлы, выполнить Alembic `upgrade head`, запустить сервер. Не заменять SQLite-файл архивом — пользовательская база должна сохраниться на диске.
3. Для будущего HTTPS: настроить `PUBLIC_BASE_URL`, защищённые cookie, ключ шифрования, PostgreSQL и **явный доверенный прокси**. Подробности — `SCALING_AND_PROXY_RU.md`.
4. Для коммерческого запуска: обновить устаревший React 16 до поддерживаемой версии, запустить CI Postgres, испытать восстановление из backup, проделать авторизованный интеграционный тест каждой соцсети, проверить права Meta/Авито и заказать аудит безопасности.

Публикация на сервере и биллинг намеренно **не выполнялись**.
