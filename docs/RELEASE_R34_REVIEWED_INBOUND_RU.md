# OSMANX OMNICHAT R34 — сериализация входящих и проверяемое восстановление

**Дата:** 5 ноября 2026. **Локальная инженерная версия:** `3.4.0-recovery`. Развивает существующий восстановленный проект R19–R33. **Это не production-развёртывание.**

## Четыре крупных блока реализации

### 1. Межсерверная блокировка входящего аккаунта

В `backend/app/inbound_jobs.py` реализована атомарная блокировка одного `ChannelConnection` перед захватом `InboundJob`.

- `inbound_processing_token`, `inbound_processing_job_id`, `inbound_processing_until` — новые колонки в `channel_connections`.
- Сначала SQL `UPDATE` с проверкой свободного/истёкшего захвата, затем CAS задания **в одной транзакции**. Если захват задания не удался, вся транзакция откатывается и аккаунт остаётся свободным.
- Два обработчика не должны одновременно подтверждать обработку разных сообщений одного подключённого аккаунта. Разные аккаунты сохраняют независимую обработку.
- Успешная запись сообщения и освобождение канальной блокировки происходят одной транзакцией. Если старый обработчик потерял блокировку, его незавершённые изменения откатываются.
- При паузе или ошибке блокировка снимается только по текущему токену владельца. Зависший захват может быть замещён по истечении TTL 120 секунд. Для долгой обработки после истечения TTL возможен откат и безопасный повтор входящего, но не повтор внешней отправки.

### 2. Немедленный разбор повреждённых входящих

Вместо пяти заведомо бесполезных попыток теперь:

- недоступный ключ расшифрования → `failed`, код `encryption_key_unavailable` после первой попытки;
- расшифрованный, но повреждённый объект события → `failed`, код `invalid_encrypted_event`;
- шифротекст сохраняется до окончания технического срока хранения; его можно вручную вернуть в очередь после устранения причины;
- в API и логах отсутствуют исходные сообщения и ключи шифрования.

**Важно:** ошибка ключа — не повод удалять событие. Сначала восстановите прежние ключи и только потом запускайте повтор.

### 3. Двухфазное подтверждение массового восстановления

Добавлены маршруты:

- `POST /api/operations/inbound/retry-batch/preview` — проверка до 25 подходящих событий выбранного канала; интерфейс использует ограничение 20. Возвращается только количество и подписанное доказательство плана без текста сообщений.
- `POST /api/operations/inbound/retry-batch-confirm` — атомарный возврат **ровно утверждённого набора** событий. Проверяются сессия, компания, сотрудник, канал, срок действия 90 секунд, HMAC-подпись и состояние очереди.
- При одновременном изменении статусов или повторной отправке подтверждения сервер возвращает `409`; никакой лишний набор событий не запускается.
- Роли: owner/admin. CSRF обязателен. Каждое успешное действие записывается как `inbound.reviewed_batch_retry` с причиной.

Старый совместимый маршрут `retry-batch` не удалён; новый интерфейс использует двухфазный протокол.

### 4. Операционная диагностика и интерфейс OBSIDIAN

На русском тёмном экране **«Контроль доставки»**:

- показатель активных обрабатываемых аккаунтов и зависших захватов;
- поканальное состояние «занят / свободен» с предупреждениями о зависших операциях;
- понятные категории ошибок шифрования и повреждённых событий вместо сырых исключений;
- предпросмотр массового восстановления с числом событий, сроком подтверждения, кнопкой обновления и обязательной причиной;
- сохранена адаптация под ПК, 390 и 320 px.

## Обновление

1. Остановите **все** старые API и фоновые worker-процессы R33.
2. Создайте и проверьте резервную копию базы, отдельно сохраните действующий и предыдущие ключи `INTEGRATION_ENCRYPTION_KEY`.
3. Установите R34 в новую папку. Не смешивайте процессы R33 и R34 на одной БД.
4. Выполните `alembic -c backend/alembic.ini upgrade head` и `alembic -c backend/alembic.ini check` с настроенным `DATABASE_URL`.
5. Запустите локальное приложение через `start_windows.bat`/`start_linux.sh`; откройте `http://127.0.0.1:8000`.

**Ограничения:** PostgreSQL с несколькими реальными серверами, React 19 как активный бандл, настоящие официальные аккаунты соцсетей, внешний аудит безопасности, production-деплой и платежи пока не подтверждены. Не подключайте боевые аккаунты до независимой проверки.
