# OSMANX OMNICHAT R23 — восстановление отправки после аварии

**Дата:** 5 ноября 2026 года. **Статус:** локальная инженерная сборка, не публичный SaaS. Реальные соцсети, платежи и публикация не подключались.

## Главное улучшение

В прежней версии зависшая фоновая отправка всегда переходила в статус «результат неизвестен». Теперь система различает два принципиально разных случая.

**Авария до сетевой отправки.** Каждая новая попытка получает случайный `claim_token`, который записывается вместе с моментом захвата. До вызова API соцсети обработчик отдельно сохраняет `send_started_at`. Если обработчик прервался, а отметки начала сетевого запроса **нет**, задание можно безопасно вернуть в очередь: удаляется старый захват, возвращается один неиспользованный счётчик попыток, через короткую паузу сообщение снова становится доступным. В журнале фиксируется событие `outbox.recovered_before_send`.

**Авария после возможного сетевого запроса.** Если `send_started_at` уже записан, площадка могла принять сообщение. Такое задание **не отправляется повторно автоматически**. Оно помечается `uncertain`, а руководитель сверяет исходную площадку перед ручным закрытием. Журнал хранит событие `outbox.uncertain_after_interruption`.

**Обновление из R22.** Старые задания в статусе `processing` не содержат `claim_token`; даже после миграции они сознательно считаются потенциально отправленными. Это важная защита от повторной отправки сообщений, начатых прежней версией.

## Защита при нескольких обработчиках

1. `claim_token` уникален для каждой попытки, SQL выбирает `queued` → `processing` через compare-and-swap.
2. Фоновая задача обновляет `claimed_at` через **отдельную** SQL-сессию каждые 15 секунд, в том числе во время ожидания ответа API.
3. Устаревший обработчик больше не может поставить отметку начала отправки, если другой процесс уже восстановил или изменил исходное задание.
4. После ответа провайдера статус и связанное сообщение меняются одной SQL-транзакцией **только при сохранении права на захват**. Поздний ответ бывшего обработчика не переписывает результат ручной сверки.
5. Очередь по-прежнему распределяет работу между компаниями, уважает паузу площадки `HTTP 429`, сохраняет проверки WhatsApp-шаблонов и не запускает повтор для неопределённой доставки.

**Ограничение:** ни SQL, ни heartbeat не могут дать магическую гарантию exactly-once для чужого HTTP API. После возможности отправки обязателен карантин/сверка. Heartbeat уменьшает ложные срабатывания при медленном провайдере, но не заменяет реальную квитанцию о доставке.

## Операции для руководителя

На экране **«Контроль доставки»** статус `processing` уточнён:

- «Подготовка до отправки» — внешняя попытка ещё не началась.
- «Запрос передан площадке» — перед вызовом API была зафиксирована отметка возможной отправки.
- «Восстановлено безопасно: N» — число автоматических возвратов из стадии подготовки за последние 7 дней (показывается только при N > 0).
- «Требует проверки» — исходный сервис мог принять запрос; не отправляйте повторно наугад.

Информация ограничена своей компанией. `claim_token`, идентификаторы серверных процессов и ключи интеграций не выводятся клиентам.

## Улучшение совместной ручной сверки

Действие руководителя «Проверить результат» теперь использует атомарное сравнение статуса `uncertain`. Если коллега уже принял решение, второму возвращается **HTTP 409**, а не производится молчаливая перезапись. Статус исходящего сообщения изменяется в той же транзакции; при конфликте выполняется rollback.

## Обновление и резервирование

Новая миграция `f23000a10001_outbox_send_checkpoint.py` добавляет только два nullable-поля `outgoing_jobs.claim_token` и `outgoing_jobs.send_started_at`. Старые сообщения, организации и каналы не удаляются.

1. Остановите старые R22 worker и API, чтобы **не смешивать версии**.
2. Создайте отдельную проверенную резервную копию PostgreSQL/SQLite с исходными данными.
3. Разверните новый код, примените `PYTHONPATH=backend python -m alembic -c backend/alembic.ini upgrade head`.
4. Убедитесь, что Alembic head — `f23000a10001`, затем запускайте сервер и worker.
5. Откройте «Контроль доставки» и сверяйте неизвестные результаты вручную.

Локальный стартовый скрипт содержит проверку резервирования перед SQLite-миграцией, но **ручная резервная копия перед крупным обновлением всё равно рекомендуется**.

## Что ещё остаётся

- Фактическая доставка через WhatsApp/Instagram/Авито и другие официальные API **не проверялась в живом аккаунте**.
- PostgreSQL 16 двухпроцессный тест добавлен в GitHub Actions (`verify_r23_postgres.py`), но **в этом контейнере PostgreSQL и Docker не запускались**.
- React 19 не активирован: npm registry недоступен (`EAI_AGAIN`); проверенный интерфейс по-прежнему использует React 16.
- Отдельный независимый security-аудит, многосерверный нагрузочный тест, публичный деплой и платежи **не выполнялись**.
